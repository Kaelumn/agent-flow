# 下期规划：运行生命周期

> 状态：**已规划，未实现**。本文记录设计与已确认的决定，开发前以本文为准。

## 1. 要解决的问题

目前的设计假设"一个 agent 一口气把运行从头跑到尾"，但真实的 SOP 运行时间长，而且涉及多个参与者（agent、人、外部系统）。现状有三个缺口：

1. **卡死**：agent 执行到一半崩溃或超时，运行永远停在 `running`，没有超时、接管或续跑机制。
2. **重复写入**：失败后只能整个重跑；重跑会重复执行写操作（重复建账号、重复建工单），因为没有幂等保护。
3. **不等人**："人工任务"只是发一条 Teams 消息，流程不会等人确认；高风险写操作前也没有审批关卡。

另外，验证中发现"每步只调用一次工具"仅靠 skill 约束无法完全保证（有一次运行重复调用了同一个只读工具），需要系统层面的机制配合。

## 2. 设计

### 2.1 租约：解决卡死

- 每个运行有**持有者**（执行它的 agent）和**租约到期时间**。`run_current`、`run_submit` 等调用会自动续约，默认续 10 分钟。
- 后台每 30 秒检查一次，租约过期的运行标记为 `stalled`，并推送到"需要处理"列表。
- 停滞的运行可以被接管：agent 调用 `run_resume` 取得租约后从当前步骤继续；人也可以在界面上"重新分派"或"取消"。
- 租约保证同一时刻只有一个 agent 推进同一个运行。

### 2.2 两阶段步骤：解决"不知道那一步执行了没有"

最难的情况：工具已经执行（比如账号已建好），agent 在汇报前崩溃了。把每一步拆成两阶段：

```
run_begin(runId, nodeId, args)   调用工具之前，先登记要用的参数
调用工具
run_submit(runId, nodeId, outcome, edgeId)
```

接管时，如果发现某一步是"已开始、未完成"，系统会告诉新的 agent"这一步可能已执行，参数是 X"，然后按节点设置处理：

| 节点设置 | 接管时的处理 |
|---|---|
| 只读工具 | 直接重新执行 |
| 写工具，有检查动作 | 先执行节点上配置的检查（比如账号是否已存在），已存在就视为成功，否则执行 |
| 写工具，无法检查 | 暂停，交给人确认 |

系统为每一步生成**幂等键**（运行 ID + 节点 ID + 尝试次数），放在步骤信息里。支持幂等键的工具可以直接用它防止重复执行。

### 2.3 重试

- **自动重试**：节点可以配置针对临时性错误的重试策略（比如 `ServiceUnavailable` 等 30 秒后重试，最多 3 次）。只允许用于只读工具，或有幂等保护的写工具。由服务端告诉 agent 何时重试，而不是直接进入失败分支。
- **从某一步重试**：运行失败后，人在界面上选择"从这一步重试"。之前已成功的步骤和结果保留，只从失败的步骤重新开始，不重复前面的写操作。
- 每次尝试都记入运行轨迹。

### 2.4 人工节点

新增节点类型 `human`：

| 形式 | 用途 | 出边 |
|---|---|---|
| 审批 `approval` | 高风险写操作前的关卡 | 批准 / 拒绝 / 超时（可选） |
| 人工任务 `task` | 必须由人完成的事；可附表单让人填回结果（如分配的分机号），后续步骤可以用 `{{...}}` 引用 | 完成 / 无法完成 / 超时（可选） |

运行到人工节点时：

1. 运行进入 `waiting`，agent 释放租约并结束本轮执行，不空等。
2. 通知处理人（Teams 消息加界面链接）。
3. 处理人在"待办"页面处理；处理人、时间、决定、填写内容记入运行轨迹。
4. 可设置时限和升级规则（比如 24 小时未处理走"超时"分支、通知主管）。
5. 处理完成后，通过 webhook 唤醒 agent 继续执行（见第 4 节待确认项）。

简便写法：工具节点可以勾选"执行前需要审批"。校验器对"标记为破坏性（MCP `destructiveHint`）的写操作却没有审批"给出警告。

### 2.5 运行状态

```
                ┌──────── 人工处理完成 ────────┐
                ↓                               │
running ──→ 到达人工节点 ──→ waiting ───────────┘
   │  └─ 租约过期 ──→ stalled ──→ 被接管 ──→ running
   ├─→ completed / stopped / failed ──→（从某一步重试）──→ running
   └─→ cancelled
```

界面新增"需要处理"收件箱，集中显示：停滞的运行、等待审批或人工任务的运行、失败的运行。

### 2.6 数据模型变更（预估）

| 表 | 变更 |
|---|---|
| `runs` | 新增 `lease_owner`、`lease_expires_at`；状态增加 `waiting`、`stalled` |
| `run_steps` | 新增 `state`（进行中 / 已完成）、`attempt`、`started_at`、`idempotency_key`、`actor` |
| 新表 `human_tasks` | 人工节点的待办：处理人、时限、决定、表单结果、处理时间 |

MCP 新增工具：`run_begin`、`run_resume`；REST 新增：待办查询与处理、从某一步重试、重新分派。

## 3. 已确认的决定

| 事项 | 决定 |
|---|---|
| 审批人和人工任务处理人 | **MSPbots 平台的用户** |
| 实施顺序 | **先做第一阶段**（不依赖外部条件，直接解决"卡死"和"重复写入"） |
| 本期是否实现 | 否，作为下期规划 |

## 4. 待确认

1. **MSPbots 平台能否接收 webhook 来触发 agent**（人工处理完成后唤醒 agent 继续执行）。如果不能，需要改为 agent 定期查询"可以继续的运行"。这决定第二阶段的唤醒方式。
2. 审批在哪里进行：Agent Flow 网页，还是直接在 Teams 卡片上操作。
3. MSPbots 用户身份如何接入 Agent Flow（单点登录或平台代为鉴权），用于确定"谁审批了"。与正式登录和权限（RBAC）一起设计。

## 5. 分阶段实施

| 阶段 | 内容 | 外部依赖 |
|---|---|---|
| 第一阶段 | 租约与接管、两阶段步骤、幂等键、节点重试策略、从某一步重试、"需要处理"收件箱 | 无 |
| 第二阶段 | 人工节点（审批、任务）、待办页面、Teams 通知、webhook 唤醒 agent | 待确认项 1 至 3 |
| 第三阶段 | 由 agent-flow 代为调用工具，使 2.2 从"尽量判断"变为"精确知道" | 连接器与凭证的提供方式 |

## 6. 验收方式

沿用本期的验证方法（模拟 MSP 租户 + 独立子 agent + 基于运行轨迹和调用日志的评判脚本），新增场景：

- agent 在写操作后、汇报前中断，由另一个 agent 接管：不得重复写入。
- 租约过期后运行进入 `stalled`，接管后能从原步骤继续。
- 临时性错误按重试策略自动重试后成功。
- 失败后从某一步重试：之前成功的写操作不重复执行。
- 审批被拒绝时走拒绝分支；超时走超时分支；人工任务填写的结果能被后续步骤引用。
